# Session log - October 2026

## 2026-10-03 (c) - the shared link now invites the person who opened it

Phase 4 work, asked for as two features. This entry covers the first; the public
indexable-trips feature was planned and **not** built this session - see the end.

**A premise worth recording, because it was in the request:** the brief described
tiyul+ as "C# backend, React frontend". It is neither - Next.js 16 end to end,
Supabase over PostgREST, trips in localStorage via `TripContext`. Nothing about
the features was blocked by that; the file-level plan was simply rebuilt against
the real stack before any code was written.

### What a shared trip now does

- **Branding.** `BuiltWithTiyul` on both `/t/` and `/join/`, linking home with
  `utm_source=share&utm_medium=trip_link`. Those parameters are on an internal
  link deliberately: a shared trip is the only page here reachable without ever
  touching the site, so the referrer is WhatsApp or nothing, and without them the
  visit it produces is indistinguishable from direct traffic.
- **A CTA for non-owners only.** Slim sticky bar on mobile, the same invitation
  inline at the bottom on desktop, primary "plan your own, free" into `/planner`
  and secondary "duplicate this trip" (duplication already existed as
  `tripFromShared`). The owner sees neither - they built the thing and sent it.
- **`/join/` is not interrupted.** One quiet footer line, and only after the
  visitor has voted or commented. RSVP and the date poll deliberately do not
  count: those are two taps somebody makes before the itinerary has done anything
  for them.

### Two traps this walked into and out of

- **`position: fixed` inside `.rise-in`.** `SharedTripView`'s root carries
  `.rise-in`, which keeps its final transform forever, and a transform creates a
  containing block - so a fixed bar nested in it is measured against the article,
  not the viewport. This is the documented trap that caught `TripWorkspace`'s
  chat bar. Same fix as that one: the bar is a **sibling** of `.rise-in` inside a
  fragment, with `clears-chat-bar` reserving its height. Measured afterwards: the
  only fixed element in that corner is the accessibility button (44px at
  x=330..374), and the bar stops at x=310 - a 20px gap, and below its z-index.
- **Owner detection without `set-state-in-effect`.** The lint rule is an error in
  this repo, so ownership reads through `useSyncExternalStore` with a no-op
  subscribe: ownership cannot change while the page is open. The server snapshot
  is `false` on purpose - the first paint is the visitor's view, because an owner
  seeing a stranger's CTA for one frame is harmless and the reverse would hide
  the invitation from every real visitor.

### The link preview, and the thing it was leaking

`sharePreview()` is now the single source for both the `og:title`/`og:description`
and the generated card, which were deriving days/cities/stops separately.

**The card used to lead with the trip's name, and that name is the owner's free
text.** A share link goes to people the owner chose; its WhatsApp card gets
forwarded onward to people they did not. The title is now generated from the
itinerary - length, city, stop count, the places worth naming - which is both
safer and a better advert than somebody's private trip name. Verified on a real
link: the name appears twice in the document body and **zero times in `<head>`**.

Two Hebrew bugs surfaced on the way, both caught by guards that already existed:

- The two-city label was built as "A and B". The conjunction is a one-letter
  prefix, so it hits the vav-doubling rule - but `hePrefix` is built for the
  prepositional prefixes, and applying it to the conjunction before a
  vav-initial name yields **three** consecutive vavs ("Venice" is exactly this
  case). Gluing the letter on by hand is what `hebrewPrefixSites.test.ts`
  rejects, and it rejected the line. Rather than invent a spelling rule, the
  label now names one city and counts the rest - which is also the format the
  brief asked for.
- `englishComments.test.ts` caught Hebrew in the new comments, twice.

### Analytics: two new events, not four

The brief asked for `share_view`, `share_cta_click`, `share_duplicate` and
`trip_created_from_share`. Only the middle two were added. `shared_trip_opened`
and `shared_trip_adopted` already measure a shared view and a share that led to a
trip, are already in the reports, and a second name for the same moment produces
two charts that disagree by a few percent forever. Worth knowing: `shared_adopt`
only fires for a browser that held **no** trips on arrival, so `share_duplicate`
is also the only signal when an existing planner copies somebody's trip.

Attribution (`lib/shareAttribution.ts`) is a separate key from the existing share
marker on purpose - that one stores a day and only for brand-new browsers,
because it is a counter. This one records **which** link, on the trip itself
(`Trip.source`), first-link-wins, consumed once, expiring after 7 days. It is
never encoded into a share link, so a trip's origin does not travel to the next
recipient and cannot form a chain of who sent what to whom.

### Verified, not assumed

Against a production build over CDP, on a real inline share link (4 days, Rome +
Venice, 11 stops): visitor gets sticky bar + 2 CTAs + attribution recorded; owner
gets none of it and no attribution. Both at 390px and 1280px. The OG card renders
at 1200x630 with the generated headline, the stop line, a 4-dot route strip with
day 1 on the right, and the "built with" line.

**One measurement artifact worth recording**, because it looked like a bug: Edge
targets in one profile share a localStorage origin, so the visitor run's
attribution leaked into the owner run and the probe read as if the owner were
being tracked. The capture script now clears storage before every navigation.

## 2026-10-03 (b) - the homepage was still selling the plan we retired

**Reported by Netanel: "the homepage still says sharing costs 19.9 a month, but /premium
sells a 49 trip card and Pro at 89.90."** Correct, and it was two separate places, both

### What was wrong

- **`components/home/SharedTripFeature.tsx`** - the shared-trip feature block, whose
  whole job is to sell the thing the trip pass is built around - priced it from
  `PREMIUM_PRICE_ILS`, per month, and badged it "הכוכב של המנוי". So the homepage and
  the pricing page disagreed about both the amount and the billing period of the same
  feature. It also printed the constant **raw**, so it rendered "19.9" where every other
  surface renders "19.90" - exactly the drift `ils()` was moved next to the constants to
  stop, reappearing in a file that never adopted it.
- **`app/premium/page.tsx`** - the `description` metadata was a hand-typed sentence
  naming the monthly plan and its price. That is the sentence Google and WhatsApp show
  **for the pricing page itself**, so the retired price was the first thing a searcher
  read about a product that no longer exists.
- **`lib/tripPass.ts`** - `tripPassPriceLabel()` claimed to match `ils()` and called
  `toFixed(2)` instead. ₪49 is precisely where those disagree, so /premium priced the
  pass "49 ₪" in all six places it mentions it while the **buy button on the trip
  screen** - the last thing read before paying - said "49.00 ₪". Display only; the
  amount PayPal charges comes from the number in `api/pass/create-order`.

All three now compute from `TRIP_PASS_PRICE_ILS` through `ils`. The homepage line reads
"49 ₪ לטיול אחד - תשלום חד-פעמי, בלי מנוי ובלי חיוב חוזר", which fixes the period as
well as the figure, and the badge now names the pass.

### The guard, and the one that turned out not to exist

`PremiumClient.tsx` carried the sentence "a browser check asserts ₪19.90 appears nowhere
on the page". **There was no such check in the repository** - it was a one-off manual
browser read in an earlier session, and it was done against the rendered body, which is
why a `description` in `<head>` was never covered by it. A comment asserting coverage
that does not exist is worse than no comment, so it has been corrected to say what is
actually true.

`src/lib/retiredPrice.test.ts` is the real guard now, two rules over `src/app` and
`src/components` with comments stripped:

- **A.** No hardcoded retired-price literal, no exceptions. Catches the metadata bug.
- **B.** No `PREMIUM_PRICE_ILS` reference, except `SubscribeButton.tsx` and
  `PremiumClient.tsx`, which share a `cta()` helper whose premium branch is dead but
  stays for the subscription path. Catches the homepage bug.

**Both rules were verified by reintroducing both bugs and watching them fail** with the
right file and line, then reverting. A guard that has never failed has not been tested.

### Checked and deliberately left alone

- **`mailEvents.ts`** still prices premium at ₪19.90 in `sendSubscriptionActivated`.
  That is correct: it fires from the subscription webhook, and grandfathered subscribers

## 2026-10-03 - the four seconds of beige screen, and the copy that read like a model

**The complaint was "the site takes a few seconds to load with a beige screen", and the
cause was not what anyone would have guessed.** The assumption behind the request was
that something is being fetched and the screen waits for it, so the fix would be
skeleton loaders. It was not. The HTML was complete and correct in **300ms**, the CSS
was done at 915ms, the DOM was interactive at 851ms - and the browser then painted
nothing at all for several more seconds.

### Measuring it honestly, which took two false starts

- The first measurement said FCP was 8,616ms. It was an artifact: the browser-automation
  extension leaves its tab **backgrounded**, and Chrome does not paint a hidden tab.
  `document.visibilityState` was `hidden`. Any paint timing collected that way is
  meaningless.
- The second attempt took screenshots to see the gap. That is also invalid:
  `Page.captureScreenshot` **forces a paint**, so it moves the number it is measuring.
  It did prove the content was ready early - a forced paint at 300ms showed the full,
  correct homepage.
- What worked: headless Edge over CDP (the recipe already in the project's memory),
  which paints normally, with `Emulation.setCPUThrottlingRate` 4x and a slow-4G profile
  - a mid-range phone. Plus a `longtask` PerformanceObserver installed via
  `Page.addScriptToEvaluateOnNewDocument`, i.e. before navigation, so nothing is missed.

That showed one **3,055ms main-thread task starting the instant HTML parsing ended**.
Isolating it by page: `/about` blocked 67ms before paint, `/chat` 675ms, the homepage
**3,904ms**. So it was not the shared layout and not HTML size (`/countries` ships 662KB
of HTML and blocks 90ms).

A CPU profile named it: **1,511ms of self time in gtag.js**. The A/B, blocking
googletagmanager at the network layer and changing nothing else:

| | first contentful paint | blocked before paint |
|---|---|---|
| gtag via `afterInteractive` | 6,700-8,732ms | 2,868-5,904ms |
| gtag blocked | 2,896-2,912ms | 1,343-1,588ms |

**Analytics was costing about four seconds of blank cream screen.**

### Why the old comment was wrong, and what replaced it

`Analytics.tsx` asserted that `afterInteractive` "blocks nothing: not the first paint,
not hydration." That was reasoning from the attribute, not from a measurement. `async`
means the script does not block the HTML *parser*; it does nothing to stop ~100KB of
third-party JavaScript from monopolising the main thread in the window where the browser
would otherwise have painted. On a fast desktop CPU the effect is invisible, which is
why it survived.

`lazyOnload` is still not the answer, for exactly the reason recorded when it was
removed: it injects the tag client-side after load, so the tag is **absent from the
server HTML** that Google's "we have not detected the tag" check reads. That was a real
problem and it was correctly fixed once already.

So the two concerns were separated, because they were never the same concern:

- **The URL stays in the server HTML**, as `<link rel="preload" as="script"
  fetchPriority="low">`. A scanner reading the markup finds the exact gtag URL. A
  preload does not execute - and executing, not downloading, was the expensive part.
- **Execution waits one frame past the first paint**, then an idle callback with a 2s
  cap so a busy tab still reports.
- **No hit is lost by arriving later.** The inline consent/init scripts still run at
  `afterInteractive` and queue onto `dataLayer`; gtag.js replays the queue when it
  loads. The loader also waits for the `gtag` the consent script defines, so the consent
  default cannot lose the race.

Verified after: **FCP 2,068-2,404ms, blocked 0-1,182ms**, and gtag still loads and
consumes the queue (`dataLayer.push` replaced by gtag.js, one request to googletagmanager).

### On the skeleton loaders that were asked for

The site already had a complete skeleton system (`Skeleton.tsx` primitives,
`TripSkeleton`, `AccountSkeleton`, `TravelerSkeleton`, `JoinSkeleton`, a route-level
`/t/[code]/loading.tsx`, skeleton rows in site search), and it follows a documented
policy. **A skeleton could not have fixed this bug**: a skeleton is in the same HTML and
starved by the same main thread, so a browser that cannot paint the hero cannot paint a
placeholder for it either. Adding them to the homepage would have added DOM and JS and
made it slightly worse.

One real gap did exist and is fixed: **`AddDayPicker` told the traveller the catalog was
empty while it was still loading.** The city list is fetched on first open, so until it
arrived `filtered.length` was 0 and the component rendered its no-results message -
"אין עיר כזו בקטלוג" - about a city the user had not finished typing. "Empty" had three
meanings sharing one message; now loading draws skeleton rows, a failed fetch says so
(and is not cached, so re-opening retries), and only a real empty result keeps the
catalog line.

- **The catalog** (`src/data/destinations.ts`, 4.18MB) was not touched. Those are
  factual descriptions of real places; rewriting ~3,400 of them for tone is how
  inaccuracy gets introduced, which is the one thing hard rule 2 forbids.
- **The admin dashboard** is internal and not a visitor surface.

### Other things measured and found fine

- Every page is statically prerendered; TTFB on the live site is 290-460ms, gzipped.
- The 3.4MB catalog **is** in a browser-served chunk, but it is loaded lazily and only

  It is not on the critical path.
- The remaining ~1.4s of pre-paint blocking is React hydration plus the Turbopack module
  loader, i.e. framework cost, not an application bug.
