# Session log - November 2026

## 2026-11-15 - the site moves off Vercel to the VPS

### (a) What was built / changed

- `deploy/` (new): everything the server needs, versioned with the code.
  - `release.sh` - runs on the server per deploy: `npm ci` + `next build`
    inside a memory-capped systemd scope (the box is shared), a smoke run of
    the new build on :4801 (health + `/` + `/chat` must render the trademark
    footer), then the `current` symlink swap, restart and health check, with
    an automatic swap back if the new release fails it. Keeps the last four.
  - `rollback.sh` - symlink swap to the previous (or a named) release.
  - `tiyulplus-web.service` - `next start -H 127.0.0.1 -p 4800`, unprivileged
    user, systemd hardening, MemoryHigh 900M / MemoryMax 1200M.
  - `tiyulplus-warm.timer` + `.service` + `warm.sh` - the `vercel.json` cron,
    same `:00/:30` schedule; the secret goes to curl on stdin, not argv.
  - `Caddyfile.tiyulplus` - apex 308 -> www and HSTS 63072000 (both were
    Vercel's, matched exactly), `flush_interval -1`, `lb_try_duration 15s` so a
    deploy restart holds requests instead of 502, `header_up -X-Real-IP`.
  - `cutover.sh` - waits until the zone's authoritative nameservers answer
    with this box's address, restarts the app (loads the env file as it is
    then), names any missing payment/mail secret, installs the Caddy block
    between its markers, validates, reloads, and confirms HTTPS locally.
  - `bootstrap.sh` - one-time, idempotent server setup.
- `scripts/deploy.mjs` + `npm run deploy` (`-- rollback | status | logs`).
  Node, not bash: on Windows `bash` on the PATH is the WSL launcher.
- `.gitattributes`: `*.sh` and `deploy/**` pinned to LF; `git archive` runs
  with `core.autocrlf=false` for the same reason.
- `next.config.ts`: the HSTS comment now names the proxy instead of Vercel.

### (b) Product decisions and why

- **Build on the server, not locally.** sharp, lightningcss and the Tailwind
  oxide binary are platform-specific; a Windows build shipped to Linux would
  fail at runtime. Measured: compile 94s, whole deploy ~2 min.
- **The app binds 127.0.0.1 only.** `requestIp()` trusts X-Forwarded-For.
  Tested against the real block in a throwaway Caddy: a spoofed XFF and
  X-Forwarded-Host are replaced, but X-Real-IP passed through as sent - not
  exploitable (it is only a fallback when XFF is absent, which Caddy never
  allows), dropped at the proxy anyway.
- **No `encode` in front of Next.** Next compresses its own responses, and a
  second compressor is one more place `/api/chat` could stall. Streaming
  measured through Caddy: first event 179ms, text spread to 20s.
- **One process, not a cluster.** The AI budget and rate limits are in-memory.
- **Cutover is gated on authoritative DNS**, because a Caddy block added
  before the switch fails ACME and backs off for up to hours.
- **Vercel "Sensitive" variables cannot be pulled** (CLI writes
  `[SENSITIVE]`), so 13 server-only secrets are filled in by hand on the server.
  Supabase URL + anon key were verified equal to production by matching the
  live JS bundle. `CRON_SECRET` was regenerated (only the timer uses it).
- **Image optimiser is unused in production** (pages load catalog photos
  straight from their hosts), so self-hosting adds no image CPU load, and no
  Blob-mirrored photos depend on Vercel.

- Until the hand-filled secrets are in: payments (PayPal), mail (Resend),

- DNS (two A records at Porkbun) is the owner's step; the watcher handles

## 2026-11-15 (later) - a self-hosted database to replace Supabase cloud

### (a) What was built / changed

- `deploy/db/` (new): the three parts of Supabase the site uses - Postgres 17,
  PostgREST, Supabase Auth (GoTrue) - in Docker on the VPS, served at
  `https://db.tiyulplus.com` with Supabase's own URL layout (`/rest/v1`,
  `/auth/v1`), so supabase-js and the server's direct REST calls need only a
  new URL and new keys. Versions follow Supabase's reference self-host compose.
  - `compose.yml` - every port on 127.0.0.1; memory caps 512/128/128/16 MB;
    measured ~50 MB in use. PostgREST's OpenAPI root is disabled.
  - `init/00-roles.sh` - the roles, schemas and grants a Supabase project has
    and the app's SQL assumes (anon/authenticated/service_role/authenticator,
    `auth` owned by supabase_auth_admin, `extensions`, Supabase's statement
    timeouts, and the event trigger that reloads PostgREST's schema cache).
  - `install.sh` - secrets generated once (JWT secret, legacy-style HS256 anon
    and service_role keys), SMTP/Google values copied from the website's env
    file, stack up, backup timer, Caddy block once DNS points here.
  - `backup.sh` + timer - nightly `pg_dump -Fc`, verified with
    `pg_restore --list`, 14 days kept.
  - `import-supabase.sh` - copies the old project: public schema whole, plus
    `auth.users`/`auth.identities` by column intersection (keeps ids, so Google
    sign-ins land in the same accounts); compares every table's row count.
    The connection string is read from stdin, never argv.
  - `Caddyfile.tiyulplus-db` - its own marker region, like the website's.
- `scripts/deploy.mjs`: `npm run deploy -- db` and `-- sql <file>` (one
  transaction - the replacement for the dashboard's SQL editor).
- `next.config.ts`: `connect-src` takes the database origin from
  `NEXT_PUBLIC_SUPABASE_URL` instead of `*.supabase.co`.
- `deploy/cutover.sh` + `install.sh`: create Caddy's log file as `caddy` before
  `caddy validate` (see (c)).

### (b) Product decisions and why

- **Netanel chose to leave Supabase cloud** ("easier for scaling") after the
  costs were laid out: no extra money on the existing box, ~1 day to set up,
  ~1 hour a month to keep. Only the three used parts are run; the full
  Supabase stack would not fit beside the other services on a 4 GB box whose
  site builds peak at 1.8 GB.
- **Sign-in stays exactly as it was for the visitor**: 6-digit email code
  (same template, `login@`, through Resend's SMTP) and Google via ID token -
  no redirect, so no client secret and no Google console change.
- **Auth runs in the host network namespace**, on 127.0.0.1. The box's
  firewall drops all forwarded traffic by design and is shared, so it was not
  loosened; Postgres and PostgREST stay on an isolated Docker network.
- **Switch order (planned):** dry-run import; Vercel production env pointed at
  the new database and built without promoting; a final fresh import; promote;
  delta count check. Vercel and the VPS then share one database, so the later
  www DNS move carries no data split. Everyone signs in once more (sessions
  are not copied).

## 2026-11-23 - growth research; public trips get a link card and a WhatsApp button

  after `על`); it now uses the bare name.

### (b) Product decisions and why

- **Public trip pages had no og:image at all.** `generateMetadata` sets
  `openGraph`, which replaces the parent's, so even /og.png was dropped and a
  forwarded /trips/ link arrived in WhatsApp as bare text. WhatsApp is 99% of
  Israelis; that preview is the most-seen ad the site has.
- **UTM on the WhatsApp link** because a chat sends no referrer: without it a
  forward is indistinguishable from direct traffic. The canonical tag already
  points at the clean URL.
- The work came out of a research pass on what drives traffic for this niche
  (kept outside this public repo). Its conclusion: distribution, not more
  features - seeded shares, answers in Israeli destination Facebook/WhatsApp
  communities, admin and micro-creator partnerships, a data-led press pitch,
  and Passover 2027 (school vacation 13-28 Apr; families book Dec-Feb) as the
  content focus. Also: Instagram (since 30 Apr 2026) and TikTok demote whole
  accounts that mostly post unoriginal content - the bot's stock slideshows fit.
