## 1. The site earns nothing today, and that is the biggest hole

`CLAUDE.md` names affiliate revenue as the business model. **Not one outbound
link carries a partner id**, and the one real booking integration is switched
off. Measured on the live homepage:

```
href="https://www.booking.com"          <- no aid, no label
href="https://www.getyourguide.com"     <- no partner_id
href="https://www.skyscanner.co.il/"    <- no associate id
```

and `GET /api/activities?city=vienna` returns `{"mode":"off"}`.

### 1.1 Turn Viator on - the smallest step to a first shekel

This one is **fully built and tested**; it needs a key and one word.

1. Sign in at <https://partnerresources.viator.com/> (Viator Partner Programme,
   free). You already have a sandbox key or the code would not mention one.
2. Complete the production application and get the **production API key** and
   your **partner id (pid)**.
3. In Vercel -> the project -> Settings -> Environment Variables, set:
   ```
   VIATOR_API_KEY=<the production key>
   VIATOR_MODE=production
   ```
   `VIATOR_MODE` is a deliberate second switch: the code refuses to use a live
   key until that word is written, so a key pasted by accident cannot start
   sending real traffic.
4. Redeploy, then check: `curl "https://www.tiyulplus.com/api/activities?city=vienna" -H "Sec-Fetch-Site: same-origin"` should return `"mode":"production"` and a non-empty `offers` array.
5. Open a trip in Vienna on the site and confirm the "דברים לעשות" panel shows
   real tours with prices.

### 1.2 The four affiliate links - and why this is more than pasting an id

`src/lib/booking.ts` has an `affiliate` slot per provider and **all six are
`affiliate: null`**. Setting the environment variable alone does nothing: the
slot has to be filled with that partner's URL shape as well. So each provider
is two steps.

Per provider, in this order (they take days to approve, so apply first):

| provider | where to apply | what you get |
|---|---|---|
| Booking.com | <https://www.booking.com/affiliate-program/v2/index.html> | an `aid` |
| GetYourGuide | <https://partner.getyourguide.com/> | a `partner_id` |
| Skyscanner | via Travelpayouts <https://www.travelpayouts.com/> (Skyscanner's direct programme is closed to small sites) | a marker |
| Airalo | <https://www.airalo.com/affiliate-program> (Impact) | a tracking link |

Once approved, for each one:

1. Read the partner's own docs for the **deep-link format**. It will be
   something like `https://www.booking.com/searchresults.html?ss={QUERY}&aid={ID}`.
2. In `src/lib/booking.ts`, fill that provider's `affiliate` object:
   ```ts
   affiliate: {
     template: 'https://www.booking.com/searchresults.html?ss={QUERY}&aid={ID}',
     idKey: 'booking',
   },
   ```
3. In Vercel set the matching variable, e.g. `NEXT_PUBLIC_AFFILIATE_BOOKING=12345`.
   It **must** keep the `NEXT_PUBLIC_` prefix - the link is built in the
   browser, and without the prefix the value is `undefined` there and the code
   silently falls back to the plain public URL.
4. Redeploy and check the rendered link actually carries the id:
   ```
   curl -s https://www.tiyulplus.com/ | grep -o 'href="https://www.booking.com[^"]*"'
   ```
   If the id is not in that string, it is not earning.

**Do not skip step 4.** A missing id fails silently and looks exactly like a
working link.

## 2. Nobody would know if the site went down

The machinery shipped today; nothing is using it yet.

### 2.1 Point an uptime monitor at the health endpoint - 5 minutes

1. Sign up at <https://uptimerobot.com/> (the free tier is enough).
2. Add New Monitor -> **HTTP(s)**.
3. URL: `https://www.tiyulplus.com/api/health`
4. Monitoring interval: **5 minutes**.
5. Under "Advanced", set it to alert when the status code is **not 200**.
6. Alert contacts: your email, and your phone if you want SMS.
7. Save, then prove it works: temporarily change the URL to
   `https://www.tiyulplus.com/api/health-nope`, wait for the alert to arrive,
   then change it back.

The endpoint returns 503 **only** when the database is unreachable. A missing
optional key returns 200 `degraded`, so this will not page you for a config
choice.

### 2.2 Prove the error alerts reach you - 2 minutes

1. Open <https://www.tiyulplus.com/admin> (sign in with natikyan153@gmail.com).
2. Find the AI spend card, press **"בדיקת התראה"**.
3. A labelled test message should arrive in the Discord/Slack channel within
   seconds. If it says `webhook_http_4xx` or "not configured", the webhook URL
   in Vercel is wrong.

From now on a real exception posts there by itself, once an hour per distinct
failure.

### 2.3 Take the first backup - 5 minutes

A backup nobody has taken is not a backup.

1. In the repo:
   ```
   npm run backup
   ```
   It reads `.env.local`. **Your local `SUPABASE_SERVICE_ROLE_KEY` is currently
   invalid** (it returns 401 - I checked), so first copy the current one from
   Supabase -> Settings -> API -> `service_role` and paste it into `.env.local`.
2. It prints a row count per table and writes
   `backups/tiyul-backup-<timestamp>.json`.
3. **Copy that file somewhere that is not this laptop** - Google Drive, a USB
   stick, anywhere. `backups/` is gitignored on purpose, because the file holds
   real travellers' names, phone numbers and email addresses.
4. Rehearse the restore once, against nothing dangerous:
   ```
   npm run restore -- backups/tiyul-backup-<timestamp>.json
   ```
   With no `--confirm` it writes nothing and prints what it would do. Read that
   output once now, so the first time you read it is not during an incident.
5. Repeat step 1 **before every SQL migration** from here on.

### 2.4 Find out what Supabase itself keeps - 2 minutes

This is the only thing that can bring accounts back; a JSON dump cannot.

1. Supabase -> the project -> **Database** -> **Backups**.
2. Write down: how many daily backups are retained, and whether
   **Point-in-Time Recovery** is available on your plan.
3. If the answer is "7 days, no PITR" (the usual free/Pro answer), that is your
   real recovery window - and `npm run backup` weekly is what extends it.

## 3. You cannot tell how many people visit

There is **no analytics of any kind** - no Google Analytics, no Vercel
Analytics, nothing. `app_events` counts exports per day and that is all. So
today you cannot answer "did anyone use the site this week", which makes every
other decision guesswork.

The privacy policy currently says the site runs no behavioural tracking, and
that is a real asset. So the recommendation is the cookieless option:

1. Vercel -> the project -> **Analytics** -> Enable. (Free tier: 2,500 events
   a month, no cookie, no consent banner needed.)
2. `npm i @vercel/analytics`
3. In `src/app/layout.tsx`, add `<Analytics />` inside `<body>`.
4. **Update `/privacy`**: add one line saying aggregate page views are counted
   without cookies and without a personal identifier. There is a test
   (`policyPages.test.ts`) that scans for tracker names and it will fail until
   the policy matches reality - that is the guard doing its job, not a bug.
5. Deploy, wait a day, and look at the dashboard.

If you would rather stay at literally zero third parties, the alternative is to
read Vercel's built-in request logs - less useful, but free of any decision.

## 4. Finish what is half-connected

### 4.1 The photo mirror - 3,309 places depend on files you do not own

Confirmed today: production serves every photo straight from
`upload.wikimedia.org`, and `NEXT_PUBLIC_PHOTO_MIRROR_BASE` is unset. **You
cannot mirror a file after it is deleted**, so this is proactive work, and it
also makes photos noticeably smaller on phones.

1. Vercel -> **Storage** -> Create -> **Blob**. Copy the read-write token.
2. ```
   export BLOB_READ_WRITE_TOKEN=<token>
   npm run mirror:photos -- --dry --limit 30     # rehearsal, uploads nothing
   ```
   Read the output. It should list files and say what it would upload.
3. ```
   npm run mirror:photos
   ```
   It is resumable - if it stops, run it again. Budget about **1GB** of
   storage and expect it to take a while. Re-run until it prints
   **"0 catalog photos still not mirrored"**.
4. Only then, in Vercel, set the variable it prints:
   ```
   NEXT_PUBLIC_PHOTO_MIRROR_BASE=https://<store>.public.blob.vercel-storage.com
   ```
5. Redeploy and verify the switch actually flipped:
   ```
   curl -s https://www.tiyulplus.com/destinations/vienna | grep -c "blob.vercel-storage.com"
   ```
   That must be greater than zero. Also check a destination page by eye - the
   photos should look sharper on a phone.
6. **Re-run `npm run mirror:photos` after every data session**, so new
   photographs get a copy while the original is still alive.

Until step 4, nothing changes - which is what makes steps 1-3 safe to do in
pieces.

### 4.2 TikTok is on a sandbox app and the bot does not exist

The authorize URL uses client key `sbaw5ymiolkzf1wb7n` - the `sb` prefix means
**sandbox**. So the connect flow can only ever authorize test accounts, and
even then `TIKTOK_BOT_URL` points at an endpoint that was never built.

Decide which of these you want:

- **Finish it:** apply for production access in the TikTok developer portal,
  swap `TIKTOK_CLIENT_KEY`, and build the bot endpoint described by the
  `forwardCodeToBot` signature in `src/lib/server/tiktok.ts` (it receives the
  authorization code and exchanges it, so the client secret never touches this
  server).
- **Park it:** leave it. It is behind `/tiktok`, nothing links to it, and it
  costs nothing sitting there.

There is no middle option that works - a sandbox key will not post to a real
account.

## 7. Known, accepted, and deliberately not being fixed

Recorded so nobody re-opens them:

- **The 2.5MB client bundle.** Standing item.
- **`/t/<code>` has no rate limit.** It is the viral surface and many Israelis
  share one address behind carrier NAT; limiting it would break sharing to
  prevent something cheap.
- **`/t/%%%` returns 500.** A malformed percent-escape fails inside Next's own
  param decoding, before any of our code runs. Not a link anyone shares.
- **`/api/cities` is unmetered.** It reads an in-memory catalog: no database
  call, no money.
- **352 places have no photograph.** 61 are kosher venues (confirmed
  unfillable across four sessions), 175 have had every retrieval method run
  against them, and 116 remain genuinely tryable.
- **131 of 166 destinations have no kosher place.** Stated honestly on each
  page rather than padded.
- **Marrakech is skipped** because direct TLV flights cannot be verified.
